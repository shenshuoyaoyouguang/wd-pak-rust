# wd-pak Windows 图形界面技术栈规划

> 状态：**决策稿（spike 部分通过：S1–S5 已落地待人工签收，S6–S8 未开始，见 §5.1）**｜依据：`docs/windows-ui-plan.md`、`docs/windows-ui-impl-plan.md`｜代码基线：`main` @ `b832f97`
> 本文只决定实现技术与平台集成方式，不改写界面行为；界面规格仍以 `docs/windows-ui-plan.md` 为唯一来源。
> 与既有约束的关系：CLI 的 Windows 平台口径、静态单 exe、MSI 分发沿用 `docs/windows-plan.md` §1.1；GUI 不改变七项 CLI 能力与退出码。

## 0. 结论摘要

| 项 | 结论 |
| :--- | :--- |
| 推荐方案 | **Win32 原生控件 + Rust**：复用现有库与 `windows-sys`，按需增加 `windows` 作为 Windows 专属依赖 |
| 运行时 | **零额外运行时**：不引入 WebView2、.NET、VC++ Redist，不增加安装期依赖 |
| 界面框架 | 不采用第三方 UI 框架；原生控件承担菜单、标签、列表、树、对话框，只有详情与预检问题区做最小自绘 |
| 备选方案 | **Slint**：若交付周期优先且许可通过；**egui** 只做一次性原型；**Tauri/WebView2** 与 **WinUI 3** 不选 |
| 决策门槛 | 先做 3–5 人日 spike，覆盖 §5 的八项 S1–S8；S3/S4/S5 与 S8 全部通过再全面开工 |
| 估算基线 | 以实施拆分 §3.1 的 47–61 人日为基线；原生方案预计上浮 30–50%，Slint 约 10–20%，spike 后回填 |

## 1. 约束与硬指标

## 2. 候选方案评估

评分口径：**强** = 直接满足且风险低；**中** = 可满足但需额外工作或验证；**弱** = 需要明显折衷；**—** = 不满足。

| 维度 | Win32 原生控件 | Slint | egui/eframe | Tauri 2 + WebView2 |
| :--- | :--- | :--- | :--- | :--- |
| 单 exe / 离线 | 强 | 强 | 强 | 弱（WebView2 运行时） |
| 原生菜单、托盘、跳转列表、任务栏 | 强 | 中 | 弱 | 中（插件桥接） |
| 中文输入法 | 强 | 中（需验证） | 中（需验证） | 强（WebView） |
| 屏幕阅读器 | 强（原生控件） | 中（AccessKit，需验证） | 弱至中 | 强（HTML 语义） |
| 高 DPI / 多屏 | 强 | 强 | 中至强 | 强 |
| 暗色 / 高对比度 | 中（暗色依赖未公开属性） | 强（自绘可控） | 强（自绘可控） | 强 |
| 大列表 / 树 | 强（虚拟列表 + 懒加载树） | 中（列表可虚拟化，树需自建） | 强（自绘虚拟列表） | 强 |
| 开发效率 | 弱 | 中至强 | 强 | 强 |
| 许可与供应链 | 强（仅系统 API 绑定） | 中（GPL/商业双许可，需法务确认） | 强 | 强 |
| 体积 / 启动 | 强 | 中 | 中 | 弱 |

**结论性判断**：

1. 硬指标里“零运行时、原生托盘/跳转列表/拖放、中文输入、屏幕阅读器”同时满足的，只有原生控件。其他方案至少有一项需要额外运行时、额外桥接或未验证的辅助技术。
2. 原生方案的代价集中在开发效率与暗色主题；这两项都可以通过“尽量用系统控件、只对少数区域自绘”和 spike 提前验证来控制。
3. Slint 是唯一在开发效率与原生程度之间比较平衡的备选，但许可与辅助技术行为必须先确认；egui 的无障碍与中文输入风险不足以支撑验收；Tauri 的 WebView2 与单 exe/离线直接冲突。

## 3. 推荐方案

### 3.1 组合

| 层 | 选择 | 说明 |
| :--- | :--- | :--- |
| 语言与构建 | 现有 Rust 工程，新增 GUI 可执行目标 | CLI 目标不动，GUI 与 CLI 共用库层 |
| 窗口与控件 | Win32 公共控件（菜单、标签、列表、树、状态栏、工具栏、对话框） | 不引入第三方控件库 |
| 系统 API 绑定 | 现有 `windows-sys` + 按需新增 `windows`（Windows 专属依赖） | `windows` 用于 COM、Shell、OLE、辅助功能接口；按 feature 裁剪 |
| 列表 | 原生虚拟列表（owner-data） | 排序在模型层完成，控件只负责显示与命中 |
| 树 | 原生树控件，展开时懒加载子项 | 避免一次性插入大包全部节点 |
| 标签 | 原生标签控件 + 少量子类化 | 中键关闭、重排、关闭按钮由子类化实现 |
| 详情/预检问题区 | 原生静态文本与列表，必要时最小自绘 | 不自定义整套控件，保证辅助技术可读 |
| 持久化 | 本地 JSON（现有 `serde_json`） | 目录与格式由 G0-06 定义；不写注册表 |
| 并发 | UI 线程 + 工作线程，消息/通道回传 | 不引入异步运行时 |
| 打包 | 现有 MSI + 独立 exe | 不新增运行时安装步骤 |

### 3.2 选择原生控件的理由

- **无障碍是系统能力**：原生列表、树、菜单、标签由系统暴露辅助功能信息，避免为自绘控件补写提供程序。
- **输入法零适配**：系统编辑控件直接支持中文候选窗与组词，不需要自行处理 composition 事件。
- **Shell 集成完整**：托盘、跳转列表、任务栏进度、系统通知、文件对话框、OLE 拖放都在同一套 API 内。
- **交付形态不变**：没有 WebView2、.NET、VC++ Redist，Windows 10 1809 干净机器可直接运行。
- **与现有代码同语言**：GUI 直接调用 `PakSession`、`browse`、`workspace`、`recent` 与写入核心，不需要进程间协议或文本解析。

### 3.3 需要接受的代价

- 布局、标签条、命令栏溢出等需要自己实现；预计比声明式 UI 多 30–50% 工作量。
- 暗色模式依赖系统未公开属性，必须在 spike 中验证；失败时不能假装满足规格。
- 自绘区域需要额外处理高对比度与辅助功能；因此限定自绘范围。

## 4. 集成架构

### 4.1 目标与边界

- 保留现有 CLI 可执行目标与全部行为；新增 GUI 目标，二者共用库层。
- GUI **不解析 CLI 文本输出**：读取走 `PakSession`，筛选/排序/选中走 `browse`，标签状态走 `workspace`，最近打开走 `recent`。
- 写入类操作需要结构化结果与进度；现有命令函数的文本输出仅作为日志原文保留。G4 阶段为写入链路补结构化入口，不改变 CLI 文案与字节结果。

### 4.2 逻辑分区

| 分区 | 职责 | 不做什么 |
| :--- | :--- | :--- |
| 窗口外壳 | 主窗口、五区布局、菜单、命令栏、标签条、状态栏 | 不直接读写包文件 |
| 页面 | 工作台、浏览、校验、任务、通知、设置、帮助、账户 | 不持有工作线程 |
| 控件适配 | 虚拟列表、树、详情、问题表、日志查看器、进度与步骤条 | 不实现领域规则 |
| 平台适配 | COM、DPI、暗色、文件对话框、托盘、跳转列表、任务栏、拖放、通知 | 不分散到页面代码 |
| 任务与进度 | 工作线程、进度合并、取消、结果与日志 | 不阻塞 UI 线程 |
| 状态与持久化 | 复用 `session/browse/workspace/recent`；设置、会话、最近、任务历史的读写 | 不定义新的包语义 |

### 4.3 线程与消息

- UI 线程独占窗口与控件；工作线程只处理解析、读取、打包、解包、校验。
- 打开大包在后台解析，完成后把快照交给 UI；解析期间显示局部进度并可取消。
- 写任务串行由 `workspace` 的写标记与任务队列共同保证；进度按约 50 ms 合并后回传，避免消息风暴。
- 取消使用共享取消标记，在条目边界生效；写阶段不可中断的规则由任务实现遵守。
- 不使用异步运行时；工作线程通过标准通道或窗口消息回传，减少依赖。

### 4.4 平台适配要点

| 主题 | 做法 | 风险控制 |
| :--- | :--- | :--- |
| DPI | 应用清单声明 Per-Monitor V2；处理 DPI 变化消息；布局用 DIP 换算 | spike 覆盖 125/150/175/225% 与多屏拖动 |
| 暗色 | 窗口暗色属性 + 控件主题；自绘区域使用语义色 | spike 验证；失败则升级为阻塞问题，不静默降级 |
| 高对比度 | 跟随系统颜色，不覆盖；自绘区域使用系统颜色 | 验收含高对比度模式 |
| 文件对话框 | 系统打开/保存对话框 | 记住上次目录由 G0-06 持久化 |
| 托盘与通知 | 系统托盘图标与气泡；系统通知优先，必要时用托盘气泡 | 通知去重与前台判断在 G5 实现 |
| 跳转列表 | 系统跳转列表，最近 5 个包 | 与最近打开模型共用数据 |
| 任务栏 | 任务栏进度与失败警示 | 与任务中心状态一致 |
| 拖放 | OLE 拖入/拖出；拖出大文件先落临时文件再交给资源管理器 | 临时文件在拖放结束或超时后清理 |
| 路径 | 复用现有平台层路径规范化 | 不新增第二套路径规则 |

### 4.5 持久化

- 设置、最近打开、会话快照、任务历史存本地用户目录；格式用 JSON，字段由 G0-06 定义。
- 写入采用“临时文件 + 改名”，与现有原子写习惯一致；配置损坏回退默认并提示。
- 不把包内容或条目数据写入配置；会话只存路径、视图、选中与布局。

## 5. Spike 验证（3–5 人日）

在全面开工前，用最小可运行窗口验证以下八项；每项给出可判定的通过标准。

| 编号 | 验证项 | 操作 | 通过标准 |
| :--- | :--- | :--- | :--- |
| S1 | 五区布局与 DPI | 空壳窗口、分隔条、导航折叠；125%–225% 与双屏拖动 | 无重叠/截断/模糊；重启恢复布局 |
| S2 | 虚拟列表 | 载入 1 万条以上条目并滚动、排序 | 滚动不跳行、不冻结；排序后选中保持 |
| S3 | 中文输入 | 搜索框输入中文，使用候选窗与组词 | 组词期间不触发过滤；提交后正确过滤 |
| S4 | 屏幕阅读器 | 用系统讲述人读取列表行、树展开、菜单、进度 | 行列与状态可读；焦点顺序正确 |
| S5 | 暗色与高对比度 | 切换系统暗色、高对比度 | 控件与自绘区域可读；不覆盖系统设置 |
| S6 | 拖放 | 从列表拖出到资源管理器；从资源管理器拖入替换 | 文件内容正确；目录条目被拒；临时文件清理 |
| S7 | Shell 集成 | 托盘菜单、跳转列表、任务栏进度、系统通知 | 四项均可用；点击通知回到对应页面 |
| S8 | 交付形态 | 干净 Win10 1809 虚拟机运行单 exe | 无运行时缺失；启动与版本信息正常 |

**判定**：S3、S4、S5 任一失败且两天内无法修复，停止原生方案，转 Slint 评估；S8 失败直接停止，先解决打包与系统依赖。

## 7. 风险与应对

| 风险 | 影响 | 应对 |
| :--- | :--- | :--- |
| 原生开发量大 | 进度延后 | 限定自绘范围；优先使用系统控件；spike 后重估 |
| 暗色主题依赖未公开属性 | 规格中的暗色无法达标 | spike 验证；失败升级为阻塞项，不用“近似暗色”糊弄 |
| 自绘控件辅助功能缺失 | 无障碍验收失败 | 列表/树/菜单坚持原生；详情与问题区用原生文本 |
| 大列表的辅助功能树过大 | 讲述人遍历慢、内存升高 | 10 万行时 UIA 暴露 10 万个 DataItem；按真实包规模（数千条）验收，若仍不可接受再评估列表提供程序方案，不改变界面规格 |
| 拖出大文件需要临时文件 | 磁盘占用与清理 | 拖放结束/超时清理；失败提示；不静默残留 |
| 系统通知（Toast）实现复杂 | 通知能力不完整 | 先托盘气泡，再评估 Toast；两者都属系统通知 |
| `windows` crate 编译时间与体积 | 构建变慢 | 只开所需 feature；目标专属依赖；LTO/strip |
| Windows 10 1809 API 差异 | 老系统不可用 | 动态探测；spike 在 1809 虚机验证 |
| MSI 增加 GUI 目标 | 安装/关联变化 | 复用现有 MSI；文件关联仍为可选，不阻塞主流程 |
| Slint 许可不确定 | 备选方案不可用 | 若切换，先法务确认 GPL/商业条款 |

## 8. 不选方案与原因

| 方案 | 不选原因 |
| :--- | :--- |
| Tauri 2 + WebView2 | 依赖 WebView2 运行时；Windows 10 1809/Server 2019 不保证预装，离线安装需附带运行时，与单 exe 取向冲突 |
| WinUI 3 | 需要 Windows App SDK 运行时或自包含部署；与现有 Rust 代码分层，跨语言桥接成本高 |
| Avalonia / .NET | 需要 .NET 运行时或自包含发布；引入第二语言与第二套打包 |
| Qt | 许可与部署体积；与现有单 exe、零依赖取向不一致 |
| egui 作为最终方案 | 自绘控件的辅助功能与中文输入需要额外验证；原生托盘/拖放仍需系统桥接，省下的工作量被补齐成本抵消 |
| 第三方 Win32 控件库 | 供应链与维护风险；原生控件已覆盖主要需求，只保留最小自绘 |

## 9. 待确认项

| 项 | 影响 | 建议 |
| :--- | :--- | :--- |
| 分发范围 | 若对外分发，Slint 的 GPL 条款与原生方案的无许可风险差异变大 | 默认原生；对外分发前做许可审查 |
| 团队规模与交付周期 | 原生方案工作量大，Slint 更快 | 若周期优先且许可通过，切 Slint；否则坚持原生 |

| 暗色主题的验收强度 | 若允许“接近暗色”，原生成本下降 | 按规格执行，不接受近似 |

## 10. 决策记录

- 本稿的默认决策是**原生控件**，不是因为“原生一定更好”，而是因为硬指标里同时包含零运行时、原生 Shell 集成、中文输入与屏幕阅读器，只有它能一次性满足。
- 该决策以 §5 的 spike 为前置条件；spike 未通过时按 §5 的判定切换 Slint，不直接进入全面实现。
- 技术栈确定后，实施拆分 §8.5 中标“待外壳”的子任务即可解锁；纯逻辑层不受影响，继续按 TDD 推进。
